# Data Model Reference

## The DM module

A plugin's data inputs are driven by a **generated data model module** — a TypeScript file that describes the tables and columns of a Sisense data source. This module is used **only in `src/dev-preview-props.ts`**, which feeds the local `npm run dev` preview. It has no effect on what data the plugin fetches inside Fusion.

> **Dev preview vs production:** `DM.DataSource` in `dev-preview-props.ts` points to a data source on your local dev Sisense instance. In production — when the plugin is deployed to Fusion and added to a dashboard — `props.dataSource` is whatever data source the user's dashboard is connected to. The plugin does not know or control the production data source at build time; Fusion injects it at runtime.

## When to use the default model vs. generate a new one

The template ships with `@models/sample-ecommerce`, which covers categories, revenue, cost, quantity, dates, gender, age, brand, and country. It is a valid default for many standard chart types — bar, line, area, pie, scatter, KPI cards, and tables.

**Keep the default model when** the visualization's data requirements (the input names and types you're building for) can be satisfied by columns already in the currently-imported model. Pick the most semantically appropriate columns and update `dev-preview-props.ts` without touching the import.

**Generate a new model when** one of these is true:

- The developer explicitly named a different data source (e.g. "using Sample Healthcare")
- The visualization needs data the current model fundamentally cannot provide (e.g. two separate date columns per task for a Gantt chart, patient records, lat/lon coordinates, OHLC prices)

In the second case, tell the developer what's missing and offer to load a different source before generating.

**Never invent column names.** Only use names that exist in a model file you have actually read — either the default model (already in `dev/models/`) or one freshly generated by the CLI.

### Generating a model with the CLI

```bash
npx @sisense/sdk-cli get-data-model \
  --url https://your-instance.sisense.com \
  --dataSource "Your Data Source" \
  --token <api-token> \
  --output dev/models/your-data-source.ts
```

The generated file belongs in `dev/models/` because that directory is aliased to `@models/` in both `tsconfig.json` and `vite.config.ts`. After generating, replace the import in `dev-preview-props.ts`:

```ts
// src/dev-preview-props.ts
import * as DM from '@models/my-dataset';
// generated model
import { measureFactory } from '@sisense/sdk-data';

export const devPreviewProps = {
  dataSource: DM.DataSource,
  dataOptions: {
    category: [{ column: DM.Orders.Status }],
    value: [{ column: measureFactory.sum(DM.Orders.Revenue) }],
  },
  filters: [],
  highlights: [],
  styleOptions: {},
};
```

Every generated model exports `DataSource` (the canonical data source title) and one namespace per table. Use those namespaces to pick columns.

## Attribute types in a generated model

Not all model properties are the same type. Passing the wrong one silently compiles but produces unexpected query results or runtime errors.

### Plain column (`Column` / `Attribute`)

Text and numeric columns come out of the model as a `Column`, which extends `Attribute`. Use them directly as dimension inputs.

```ts
// Text dimension
category: [{ column: DM.Products.Category }],

// Numeric used as a dimension (group-by, not aggregated)
ageGroup: [{ column: DM.Customers.Age }],
```

`cell.data` is a `string` (text columns) or `number` (numeric columns).

---

### Date dimension (`DateDimension`) — must use a granularity level

Date columns in a generated model are typed as `DateDimension`, **not** as `Attribute`. You cannot pass a `DateDimension` directly to a dimension input — the query will fail or return unexpected results.

Always pick a **granularity level** from the date dimension:

```ts
// ✅ Correct — use a level (Years, Quarters, Months, Weeks, Days, Hours, MinutesRoundTo30, AggregatedQuarter)
date: [{ column: DM.Orders.OrderDate.Months }],

// ❌ Wrong — DateDimension itself is not an Attribute
date: [{ column: DM.Orders.OrderDate }],       // type error or runtime failure
```

Available levels (all extend `LevelAttribute`, which extends `Attribute`):

| Level              | Groups data by | `cell.data` example                  |
| ------------------ | -------------- | ------------------------------------ |
| `DateDim.Years`    | Calendar year  | `"2024-01-01T00:00:00"`              |
| `DateDim.Quarters` | Quarter        | `"2024-01-01T00:00:00"` (Q1 start)   |
| `DateDim.Months`   | Calendar month | `"2024-03-01T00:00:00"`              |
| `DateDim.Weeks`    | ISO week       | `"2024-03-04T00:00:00"` (week start) |
| `DateDim.Days`     | Calendar day   | `"2024-03-15T00:00:00"`              |
| `DateDim.Hours`    | Hour of day    | `"2024-03-15T09:00:00"`              |

`cell.text` contains a human-readable formatted string (e.g. `"March 2024"`); prefer it over `cell.data` when displaying dates.

---

### Measure (aggregation)

Measures are not columns in the model — they are created with `measureFactory` from `@sisense/sdk-data`, using a plain column as the source:

```ts
import { measureFactory } from '@sisense/sdk-data';

value: [{ column: measureFactory.sum(DM.Sales.Amount) }],
count: [{ column: measureFactory.count(DM.Orders.OrderID) }],
avg:   [{ column: measureFactory.avg(DM.Products.Price) }],
```

Common `measureFactory` functions:

| Function                            | Aggregation              |
| ----------------------------------- | ------------------------ |
| `measureFactory.sum(col)`           | Sum of all values        |
| `measureFactory.count(col)`         | Count of non-null values |
| `measureFactory.countDistinct(col)` | Count of distinct values |
| `measureFactory.avg(col)`           | Arithmetic mean          |
| `measureFactory.min(col)`           | Minimum value            |
| `measureFactory.max(col)`           | Maximum value            |

`cell.data` is always a `number` for measures. If `canFormat: true` is set on the input, `cell.text` contains the formatted string (e.g. `"$1,234.56"`); use `cell.text ?? String(cell.data)` to display.

## Updating `dev-preview-props.ts` when inputs change

The dev-preview-props file is a local-only file. Its sole purpose is to populate the plugin with sample data during `npm run dev`. When you add, remove, or rename a data input:

1. Read the file first to see which DM module is already imported and which attributes are already in use.
2. Add, remove, or rename the matching key in `dataOptions`, using attributes from the **same DM module** already imported — do not introduce a second model import.
3. For date inputs, remember to use a granularity level (e.g. `.Months`), not the `DateDimension` itself.

This file does not affect Fusion. Changes here only alter what you see in the local dev server.
